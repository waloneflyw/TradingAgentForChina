## 1. 需求背景与目标

- 参考 TradingAgents（美股多 agent 分析框架），扩展开发一个**面向 A股**的 agent 项目。
- 硬性目标：① 有自己的前端可视化；② 能部署到服务器运行；③ **实用而非 demo**。
- 原则（建议先定）：先做「**能产生真实价值的一小步**」，再横向扩展，而非一次性铺开所有功能。

## 2.6 akshare 实测结论（2026-09-10 本机实测）

| 接口 | 用途 | 结果 |
|---|---|---|
| `stock_zh_a_hist`（单只前复权日线） | 个股K线 | ✅ 快（0.2s）、稳定 |
| `stock_zh_a_spot_em`（东财全市场快照） | 5000+ 初筛 | ❌ 反爬拦截 `RemoteDisconnected`，重试仍失败 |
| `stock_zh_a_spot`（新浪全市场快照） | 5000+ 初筛 | ✅ 可用但慢（5560 行 / 19s，分页 70 次请求） |
| `stock_a_indicator_lg`（估值指标） | 估值 | ❌ 接口名已失效 → 现用 `stock_financial_analysis_indicator_em` |

**结论：**
- 单只股票数据 akshare **稳定可用** → 适合「个股深度分析」和每日增量更新。
- **全市场初筛不要依赖 akshare 实时快照**（东财反爬挂、新浪慢 19s），应**用本地 MySQL `market_daily` 一次 SQL 拉全市场历史**算指标（快、稳、不碰外部限频）。
- akshare 接口名随版本变化 → 必须封装**数据适配层 + 版本锁定 + 重试兜底**。

## 2.8 两个关键点（复权因子 / xtquant 使用）

### 复权因子
分红/送股/转增/配股会让股价在除权除息日「跳空」，这不是真实下跌。复权因子用来修正这个跳空：
- **前复权 qfq**：当前价不变、历史价下调 → 用于技术指标/看图（当前价就是真实成交价）
- **后复权 hfq**：首日价不变、之后累乘 → 用于算真实总收益率（含分红送股）
- **不复权 raw**：有除权缺口

**重要性**：均线/MACD/RSI 等价格形态指标、回测、选股因子（如「N 日涨幅」「距 52 周高点」）若用未复权价会严重失真——比如「10 送 10」会让股价瞬间腰斩，未复权看就是假跌 50%，均线/回测都会给出假信号。

**对 `market_daily`**：它只有原始 OHLC（`pct_chg` 是真实日涨跌幅、可直接用），但算技术指标必须用复权价 → 需从 akshare（`stock_zh_a_hist(adjust="qfq")` 实测可用）或 QMT 补复权价/复权因子，存到**新项目自己的表**（不动 fastapi_db）。

### xtquant 使用（已验证 ✅）
- **可用环境**：`D:\py\python.exe`（Python 3.12.8）+ `D:\py\Lib\site-packages\xtquant`（自带 cp36~cp313 的 .pyd，Python 3.13 也可用）。
- **已跑通**：连接 miniQMT（`127.0.0.1:58610`）→ 交易日历、个股详情、历史日线、实时 tick 全部取到。
- **⚠️ 取历史 K 线必须先 `download_history_data(代码, '1d', 起, 止)` 再 `get_market_data_ex`**（miniQMT 不自动下历史，否则返回空）。
- **复权已验证**：`get_market_data_ex(..., dividend_type='none'|'front'|'back')` —— 前复权把历史价下调（600025 首日 9.570→8.985）、当前价不变，正好补 `market_daily` 缺的复权。
- **局限**：`get_authorized_market_list` 本客户端不支持（东北证券测试版），不影响取数。

## 3. 功能 brainstorm（从单股分析向外扩展）

分三层，建议 MVP 只做第一层 + 第二层的「标签选股」：

**L1 个股深度分析（已有，A股化）**
输入股票代码 → 多 agent 分析 → 报告 + 五档评级（买/增持/持有/减持/卖）。

**L2 选股 / 推荐（用户重点问题）**
- 标签体系：风险偏好（激进/中性/保守）× 收益风格（高股息 / 高成长 / 低估值 / 技术突破）× 板块/行业。
- 关键架构：**「量化初筛 → LLM 精析」两层漏斗**，不是 LLM 全市场扫描。
  - 全市场 5000+ 只，逐只用 LLM 分析不现实（贵且慢）。
  - 先用规则/指标打分筛出几十只候选池，再用 agent 深度分析排序。

**L3 组合 / 监控 / 回测（进阶）**
- 自选股监控：定时跑分析，变化推送预警。
- 大盘/板块/行业研判：每日市场情绪、板块轮动、北向资金、政策面。
- 建议→回测→记忆闭环：agent 出的信号用 QMT/历史数据回测验证，把结果写回记忆（复用 TradingAgents 的 `reflect_and_remember`）。

**L4 工程化（贯穿）**
- 用户系统 + 历史报告持久化 + 定时任务调度 + 推送（前端/微信/钉钉）。

## 8. 指标筛选与利用（两层）

**量化初筛层（规则/打分，不靠 LLM）**
- 价值：PE、PB、股息率、ROE、PEG
- 成长：营收/净利增速、毛利率趋势
- 技术：均线多头、MACD 金叉、RSI、量价配合
- 风险：波动率、换手率、市值、ST/退市风险（负向过滤）
- 产出：给每只股票打「高股息/高成长/低估值/技术强势」标签 → 候选池。

**LLM 精析层（对候选池深度分析）**
- 复用 §6 的多 agent 流水线，输出理由 + 评级 + 排序。

## 11. 持久化设计（笔记 #2：哪些数据要持久化、用什么技术）

### 需要持久化的数据（按重要性）

| # | 数据 | 来源 | 用途 | 存储 |
|---|---|---|---|---|
| 1 | 行情日线 + **复权因子** | QMT/akshare → 自有表 | 技术指标/回测/选股 | MySQL |
| 2 | 股票基础信息（行业/板块/上市日/ST） | 复用 `stocks` + 申万行业 | 选股过滤/展示 | MySQL |
| 3 | 财务/基本面（三大报表、PE/PB/ROE/增速） | akshare/tushare | 估值/成长分析 | MySQL（按季度增量）|
| 4 | 新闻舆情 + 情绪打分 | 巨潮/股吧/财联社/雪球 | 情绪分析 | MySQL（source+url 去重）|
| 5 | **分析报告**（个股 + 选股结果） | agent 输出 | 前端展示/历史回溯 | MySQL（JSON 列）|
| 6 | **agent 过程 trace** | LangGraph 事件 | 流程可视化（笔记 #5）| MySQL（JSON 列）或文件 |
| 7 | 用户 / 自选股 / 订阅 | 用户系统 | 个性化 | MySQL |
| 8 | 任务 / 调度状态 | 调度器 | 定时任务/重试 | MySQL（MVP 不引 Redis）|
| 9 | 回测 / 验证结果 | 回测引擎 | 指标有效性 | MySQL |
| 10 | 记忆 / 教训 | reflection | 复用 TradingAgents 记忆 | BM25/向量 |

### 技术选型（建议）
- **MVP 全 MySQL**：报告、trace 用 **JSON 列**（MySQL 8 支持 JSON 索引），不引入 MongoDB/ES，降低运维复杂度。
- **独立新库**（如 `ashare_agent`）：只读连接 fastapi_db 的 `market_daily`/`stocks`，自己的表（报告/trace/复权/财务/新闻/用户）建在新库——**绝不改 fastapi_db**。
- 行情表唯一键 `(code, date)`；复权因子表 `(code, date, factor)`（补 `market_daily` 缺的复权）。
- ❓ 记忆检索（第 10 项）：TradingAgents 用 BM25 关键词，中文 A股术语效果待验证，可能需换向量库（见 §10）。

### 落库 vs 运行时获取（判断标准，2026-09-11）

**四问判断**：①需全市场批量检索？②需历史序列？③复用频率高？④是横截面快照？—— 任一为「是」就落库。

**✅ 落库（数据管道定时增量）**：行情日线+复权因子、财务三表+指标、公告列表（正文按需解析）、新闻快讯（全市场滚动）、千股千评/人气榜、龙虎榜/北向、申万行业分类。

**⚡ 运行时获取（agent 现场拉）**：盘中实时价/盘口/tick（QMT）；冷门股库里缺失或过期时现场增量拉一次。

**🚫 不落库（派生现算）**：技术指标（由落库 K线用 stockstats 现算）、情绪打分（LLM 现场算）。

**核心原则：落库为主 + 运行时兜底刷新** —— 工具默认查库，缺失/过期再现场拉并落库。工具映射：`get_stock_data`/`get_fundamentals`/`get_news`/`get_announcements`=查库；`get_indicators`=现算；`get_stock_screener`=纯 SQL。

## 12. 前端可视化 & Agent 流程可视化（笔记 #5：硬性要求）

用户明确：「agent 流程可视化非常重要，必须展示 agent 思考过程，把依据（数据来源、分析报告）清晰展示给用户」。

### 必须展示的三层
1. **流程层**：多 agent 流水线（市场/情绪/新闻/基本面分析师 → 多空辩论 → 研究经理 → 交易员 → 风控三人组 → 基金经理 → 最终决策），每个节点状态 / 耗时 / token 消耗。
2. **依据层**：每个 agent 的思考过程（LLM 输出）、调用了哪些工具、每个数据点来自**哪个源**（QMT / akshare / MySQL）、字段与更新时间。
3. **结论层**：最终评级 + 各分析师报告全文 + K线/指标图表。

### 数据采集方案
- 后端用 LangGraph `astream` / 回调捕获每个节点事件 → 存 trace（§11 第 6 项）→ 前端 **SSE / WebSocket** 实时看 agent 跑（或跑完拉全量）。
- trace 字段：`node 名、输入、工具调用(名称+入参+结果摘要)、LLM 输出、耗时、token、数据来源标注`。

### 前端技术栈（对比）

| 方案 | K线/指标图 | 流程图 | 上手/生态 |
|---|---|---|---|
| **Vue3 + ECharts + AntV X6** | ECharts candlestick + MA/MACD 叠加 | X6 或自绘 SVG | 生态大、中文资料多 ✅ |
| React + ECharts + ReactFlow | ECharts | ReactFlow 节点图 | 复杂交互更强 |
| 自研 Canvas | 全自研 | 全自研 | 灵活但成本高 |

- 建议：**Vue3 + ECharts（K线/指标叠加）+ 流程图自绘 SVG 或 AntV X6**；K线用 ECharts `candlestick`，叠加 MACD/RSI/BOLL。

### 流程可视化「改动思路」关键点（已拍板：SSE 实时推流 + Vue3 + ECharts + 自绘流程图）

- **为什么现在看不到思考过程**：每个分析师是「Agent ⇄ 工具」多轮循环（`setup.py` 条件边），中间每一步的 LLM 输出和工具调用只临时存在 `messages` 里，跑完被 `create_msg_delete()` 清空，只剩最终 `*_report` 字段。
- **要抓什么**：① LLM 每次决定调哪个工具（tool_calls）；② 工具返回的数据（来源/区间/行数）；③ LLM 中间过渡分析文字。
- **怎么抓（最小侵入）**：把执行入口 `graph.invoke(...)` 换成 `graph.astream(input, version="v2")`（astream_events），流式拿到 `on_chat_model_*`/`on_tool_*` 事件，且每个事件自带 `metadata["langgraph_node"]` 标注所属 agent → **不用改任何 agent 的 prompt/逻辑**。备选方案：自写 `BaseCallbackHandler` 在构造 LLM 处挂 `callbacks=[...]`。
- **数据流**：astream 事件 → 后端中间层（①追加进 trace 列表存 MySQL JSON；②push 到 SSE 队列）→ 前端订阅 `/api/analysis/{task_id}/stream` 实时更新流程图。
- **前端三层展示**：流程层（11 节点状态/耗时/token）→ 依据层（点开节点看"调了啥工具→返回啥→LLM 说啥"，每步标数据来源 QMT/akshare/MySQL）→ 结论层（五档评级 + 各分析师报告 + ECharts K线）。
