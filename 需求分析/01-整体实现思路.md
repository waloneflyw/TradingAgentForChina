## 0. 一句话目标

把 TradingAgents（美股多 agent 分析框架）改造成**面向 A股的多智能体分析服务**，带前端可视化、可部署到服务器、实用优先。MVP 只做「个股深度分析 + 标签选股」。

## 1. 三硬目标与两原则

**硬目标**
1. 有自己的前端可视化（K线/指标图 + agent 流程可视化 + 报告展示）
2. 能部署到服务器运行
3. 实用而非 demo

**两原则**
1. 先做「能产生真实价值的一小步」，再横向扩展，不一次性铺开。
2. 尽量复用已有资产（TradingAgents 编排层、`fastapi_db.market_daily`/`stocks`、QMT、DeepSeek），只替换「美股专属」的部分。

## 2. 整体架构（四层 + 新服务边界）

参考项目是干净的四层：表现层 → 编排层 → 智能层 → 数据层。A股化后**保留前三层，重写数据层，并新增「后端 API + 前端 + 持久化」**：

```
┌───────────────────────────────────────────────────────────┐
│ 表现层  前端 Vue3（聊天框 + K线/指标图 + 流程图 + 报告）     │
├───────────────────────────────────────────────────────────┤
│ 服务层  FastAPI（分析/选股/任务/报告 API + SSE 实时推流）   │  ← 新增
├───────────────────────────────────────────────────────────┤
│ 编排层  ① 金融助手（对话路由 →「调用同事」）               │  ← 新增
│         ② 能力子图：个股分析 11-agent / 选股两层漏斗       │
├───────────────────────────────────────────────────────────┤
│ 智能层  11 个 A股化 Agent（prompt 改写 + 中文记忆）         │
├───────────────────────────────────────────────────────────┤
│ 数据层  A股版 tools（薄壳）→ route → QMT/akshare/MySQL     │  ← 重写
└───────────────────────────────────────────────────────────┘
```

**技术栈定案**

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python + FastAPI + LangGraph | 复用 TradingAgents 的 graph/agents/llm_clients |
| 金融助手 | LangGraph 工具型 router agent（对话编排层） | 三条交互路径 + 6 工具，见 §2.6 |
| LLM | DeepSeek（deep=`deepseek-v4-pro` / quick=`deepseek-v4-flash`） | 双模型分级，❓ 可选混 Qwen |
| 数据库 | MySQL 8.0，新库 `ashare_agent` | 只读 `fastapi_db` 的 market_daily/stocks，自己的表建新库 |
| 数据源 | QMT/xtquant 主 + akshare 兜底 + `market_daily` 历史 | 落库为主、运行时兜底刷新 |
| 前端 | Vue3 + ECharts + 自绘 SVG 流程图 | 聊天框为默认首页 |
| 实时 | SSE | 硬性要求：展示 agent 思考过程 + 数据来源 + 报告 |
| 部署 | 单机 FastAPI（进程内 asyncio，方案 A），后 Docker 化 | 并发模型见 §2.5 |

## 2.5 并发与异步架构（面向多用户）

> 定位：参考项目 TradingAgents 是「单用户、同步、一次性 CLI」，没有任何并发/异步能力。我们的服务要在网上面向多用户，必须补齐这一层。本节是阶段 4（FastAPI 后端）的架构前置。

### 核心认知（先摆正，再谈选型）

- **异步 ≠ 把一次分析拆成异步**。一次分析 = 4 分析师×多轮工具循环 + 两场辩论 + 若干 LLM 调用，耗时分钟级，天然是「长任务」。
- **真正的多用户并发靠三件事**：① 任务隔离（每个用户一次分析 = 一个独立 task）② 后台执行引擎（并发调度这些 task）③ 每数据源的连接池/限流（防打爆数据源）。
- **本服务是 I/O 密集，不是 CPU 密集**：绝大多数时间在「等 DeepSeek 返回 / 等 akshare/MySQL 返回」，真正的「算」占比很小。这个性质决定：瓶颈在 LLM 限流和内存，**不在 CPU 核数**（Python GIL 让单进程基本只用 1 个核，I/O 密集下多核用不上）。

### 暂定方案 A（2026-09-11）

**进程内 asyncio + 线程池 + 每 task 独立图实例 + MySQL 连接池 + 每源限流信号量；先单机，后 Docker。**

适用场景：自己用 / 小圈子试用。将来用户量真上去了，把「执行引擎」抽成独立任务队列是一层可后补的独立模块（见下文升级路径）。

### 并发/异步落在五层

| 层 | 并发/异步体现在哪 | 具体做法 |
|---|---|---|
| ① 入口层 | FastAPI async 端点 + 任务化 | `POST /analysis` 只做校验 → 生成 `task_id` → 丢后台引擎 → 立即返回；用户拿 task_id 订阅流 |
| ② 任务执行层 | 每个用户一次分析 = 一个独立 task（并发核心） | 每 task 独立持有自己的图实例/config/记忆/state，互不串扰；asyncio 事件循环并发调度 |
| ③ LLM 调用层 | 网络 I/O 天然异步 | `await graph.astream(...)` 跑在事件循环上；`astream(version="v2")` 同时是 trace 采集入口，与 SSE 推流对齐 |
| ④ 数据层 | 同步库丢线程池 + 连接池 | MySQL 用 SQLAlchemy 连接池；akshare/QMT/xtquant 是同步阻塞库，包进 `asyncio.to_thread`/`ThreadPoolExecutor`，不占事件循环 |
| ⑤ SSE 推流层 | 每 task 一个 `asyncio.Queue` | 前端订阅 `/api/analysis/{task_id}/stream`，引擎每抓到 astream 事件就 `queue.put()`，逐事件推 |

### 参考代码必改的三个点（否则多用户必炸）

1. **全局 config 单例**（`dataflows/config.py` 模块级 `_config`）：多用户并发会互相覆盖配置 → 改成 per-task config 或 per-request 注入。
2. **内存态不隔离**（`FinancialSituationMemory` 纯内存 + `TradingAgentsGraph.curr_state`）：经验记忆 MVP 已定不做（见「记忆与持久化分层设计」），但会话/报告/trace 状态必须每 task 隔离 + 落库。
3. **`graph.invoke` 换 `graph.astream`**：既解决异步，又顺带满足「依据层 trace」采集（一件事办两件）。

### 容量概念（帮排期/选机器用）

- **在线用户数 ≠ 并发分析数**：100 个在线用户里可能只有几个同时点「开始分析」；浏览历史报告几乎不占资源。
- **真实瓶颈是 DeepSeek 限流**：一次分析 ≈ 20~40 次 LLM 调用；假设账号限 5 QPS，同时 10 个任务就开始排队。机器 CPU 吃不满。
- **起步机器**：1~2 核 2~4G 单机即可；峰值同时 10~30 个分析时升到 2~4 核 8G，仍走方案 A，只需加每源限流信号量。

### 将来升级路径（后补，不做 MVP）

用户量真上去了（上百用户 / 7×24 不停机 / 要 SLA），才需要：独立任务队列（Celery/arq/Dramatiq）+ Redis broker + 多 worker 横向扩展 + 任务持久化/重试。执行引擎届时抽成独立模块，不影响上层编排与前端。

## 2.6 金融助手 · 对话编排层

> 定位：金融助手是用户看到的「第一入口」，一个对话编排层（router/orchestrator agent），本身不产出分析，只负责理解意图 + 路由到两个能力子图（个股分析 / 标签选股）+ 把结果回流到对话。参考项目 TradingAgents 只有一条固定流水线，没有这层；我们新增它来承载「日常对话 + 能力调用」的体验。

### 三条交互路径（都要，缺一不可）

| 路径 | 用户怎么触发 | 金融助手做什么 | 前端表现 |
|---|---|---|---|
| ① 日常对话 | 随便问（"最近大盘怎么样"、"茅台 PE 多少"） | 直接答，或调轻量工具（get_quote / get_market_overview） | 普通聊天 |
| ② 对话路由 | 在对话里说"帮我深度分析下贵州茅台" | 工具调用路由到个股分析子图 / 选股子图 | 聊天框显示「调用同事」+ 实时过程 |
| ③ 按钮直达 | 点「个股深度分析」/「标签选股」按钮 | 跳过意图识别，直接拉起对应子图，结果回流对话 | 弹表单（输代码 / 选标签）→ 结果回到聊天框 |

- ② 和 ③ 殊途同归：按钮直达 = 对话路由的「预填参数 + 跳过意图识别」捷径，两者都走同一个能力子图，不写两套逻辑。
- 「调用同事」的效果：能力子图作为 LangGraph **subgraph** 挂在金融助手图下，子图内的 astream 事件**冒泡**到外层 → 前端在聊天框里逐条展示"同事（基本面分析师/技术分析师…）正在做啥"，与参考项目的 11-agent 流水线共用一套 trace 采集。

### 6 工具 MVP 集（最小，够用即可）

| 工具 | 作用 | 归属 |
|---|---|---|
| `search_stock` | 名称/代码 → 标准代码（模糊搜"茅台"→600519.SH） | 金融助手 |
| `get_quote` | 实时行情快照（价/涨跌幅/PE/PB/量） | 金融助手 |
| `run_stock_analysis` | 拉起个股分析子图（11-agent 流水线） | 金融助手 → 子图 |
| `run_screener` | 拉起标签选股子图（两层漏斗） | 金融助手 → 子图 |
| `get_report` | 查历史报告（本会话/用户曾跑过，可引用） | 金融助手 |
| `get_market_overview` | 大盘/板块/北向概览 | 金融助手 |

> 原则：MVP 工具只给最少的几个，别把「能力子图内部的分析师工具」和「金融助手自己的路由工具」混在一起——分析师的 get_news/get_indicators 等属于子图内部，不暴露给金融助手。

### 双入口与状态

- 前端同时提供「聊天框」和「两个能力按钮」；按钮只是快捷入口，最终都汇入聊天框的对话流。
- 金融助手保持无状态：会话上下文（对话历史/历史报告/会话产物/偏好）由后端在每次调用时注入，见「记忆与持久化分层设计」。

## 2.7 合规护栏（第一天就设计进去）

> A股分析服务是敏感场景，合规护栏不是后补的免责声明，而是贯穿「人格 → 报告 → 评级 → 兜底」四层防线。

| 层 | 生效点 | 具体内容 |
|---|---|---|
| ① 金融助手人格 | 金融助手 system prompt | 内置三条铁律：**不承诺收益、不构成投资建议、提示风险**；任何回答不暗示"稳赚/必涨" |
| ② 报告模板强制免责 | 分析报告模板 | 报告头部/尾部固定免责声明："本报告由 AI 自动生成，仅供信息参考，不构成任何投资建议；股市有风险，入市需谨慎" |
| ③ 评级措辞 | 信号处理 + 分析师 prompt | 五档评级词（买/增持/持有/减持/卖）配"相对/偏"等弱化措辞，禁止"确定性"表达（"必然上涨"→"具备一定相对优势"） |
| ④ 敏感兜底 | 金融助手 + 后端 | 命中敏感问题（荐股承诺、代客理财、内幕消息、具体点位承诺）→ 金融助手话术兜底转回免责，后端加一层关键词拦截日志 |

- 合规是「越到用户可见层越严格」：④ 兜底 > ③ 措辞 > ② 模板 > ① 人格，四层同时存在，不互相替代。
- 后端拦的是「底线」，前端/人格管的是「体验」，两层分开，但都内置。

## 5. 分阶段实现路线（8 阶段）

> 顺序原则：**先地基后高楼**——数据层是 agent 编排和前端 K线的共同依赖，所以 DB → 数据管道 → 数据层 → agent → 后端 → 前端，每阶段都有可验证产出，前端写的时候接口已真实存在。

### 阶段 0：新库 `ashare_agent` schema 设计 + 建表脚本
- **目标**：定下所有表的字段、类型、索引、唯一键，出 DDL 脚本。
- **表清单（按需求 §11）**：
  1. `daily_bar` 行情日线 + `adj_factor` 复权因子（补 `market_daily` 缺的复权）
  2. `stock_info` 基础信息（行业/板块/上市日/ST，复用 `stocks` + 申万行业）
  3. `financial_*` 三大报表 + `financial_indicator`（PE/PB/ROE/增速）
  4. `news` / `announcement` 新闻舆情 + 情绪打分（source+url 去重）
  5. `analysis_report` 分析报告（JSON 列，含检索元数据：code/industry/board/rating/date，供 B 历史报告检索）
  6. `analysis_trace` agent 过程 trace（JSON 列，供流程可视化）
  7. `user` / `watchlist` 用户与自选股
  8. `conversation` / `message` 会话与消息（对话记忆持久化 + 前端翻看历史）
  9. `task` 任务/调度状态
  10. ~~`memory` 经验记忆~~（⏸️ 后续再补，MVP 移除）
  11. `screener_pool` 选股候选池（量化初筛结果）
- **硬约束**：唯一键 `(code, date)`；只读连接 fastapi_db，绝不改它。分钟线不建表（MVP 技术面看日线足够，见阶段 2 工具）。
- **验收**：DDL 能在本地 MySQL 建库建表，能跑通一次 `SELECT` 联查 `stocks` + `market_daily`。

### 阶段 1：数据管道（落库为主）
- **目标**：把「QMT/akshare → MySQL」的增量落库跑通。
- **任务**：
  - 行情日线 + 复权因子（QMT `download_history_data` + `dividend_type`，或 akshare `adjust="qfq"` 兜底）
  - 财务三表 + 指标（akshare 东财，注意 symbol 前缀/后缀格式差异）
  - 公告列表（巨潮 cninfo 直连，orgId 查映射表、column=szse、毫秒时间戳转 Asia/Shanghai）
  - 新闻快讯（财联社 cls，md5(sha1) 签名；akshare `stock_info_global_cls` 兜底）
  - 千股千评 / 人气榜（akshare，选股初筛因子）
  - 申万行业分类（akshare `sw_index_*`）
- **落库标准（四问）**：①需全市场批量检索？②需历史序列？③复用频率高？④横截面快照？——任一为是就落库。技术指标/情绪打分**不落库**（现算）。
- **验收**：脚本能手动/定时把一只股票的全链路数据落库，且幂等（重复跑不产生脏数据）。

### 阶段 2：数据层替换（A股版 tools + route）
- **目标**：把 TradingAgents 的 `*_tools.py` 薄壳 + `interface.py` 路由，改造成 A股版。
- **A股工具清单（需求 §7）**：

### 阶段 4：FastAPI 后端 + SSE trace 采集
- **目标**：把编排层包进后端服务，跑一次分析能被 API 调用 + 实时推送过程。
- **任务**：
  - FastAPI 骨架 + 分析/选股/任务/报告 API
  - 并发模型落地（方案 A，见 §2.5）：asyncio 事件循环 + `asyncio.to_thread` 包同步数据源（akshare/QMT）+ 每 task 独立图实例 + config 去单例化 + 每源限流信号量
  - **SSE 采集（硬性要求）**：执行入口 `graph.invoke` → `graph.astream(...)`（`astream_events`），流式抓 `on_chat_model_*`/`on_tool_*` 事件，每个事件带 `metadata["langgraph_node"]` 标注所属 agent
  - **关键时机**：trace 必须在 `create_msg_delete()` 的 `RemoveMessage` 清空前抓取（每个分析师结束都会清消息）
  - trace 字段：节点名 / 输入 / 工具调用(名称+入参+结果摘要) / LLM 输出 / 耗时 / token / 数据来源标注
  - 数据流：astream 事件 → 中间层（①存 MySQL JSON ②push SSE 队列）→ 前端订阅 `/api/analysis/{task_id}/stream`
  - **trace 持久化分层（实时展示 ≠ 持久化，同一事件两条路径）**：
    - **即时流**（只 SSE、不落库）：LLM 流式 token、节点 loading 态 —— 流完即弃。
    - **结构化摘要**（落 `analysis_trace`，JSON 列）：节点生命周期（名称/状态/耗时/token）、工具调用（名称+入参+返回摘要+**数据来源标注**）。数据来源标注必须存（依据层核心）。
    - **最终产物**（落 `analysis_report`，全文）：各 agent 报告全文、最终评级。
    - **工具返回原文不存**（几十 KB CSV，随时可重查），只存摘要+来源+行数；全量存一次分析膨胀到 MB 级，摘要级仅几十 KB。
- **验收**：POST 一次分析，SSE 能实时收到各节点事件（状态/耗时/工具调用/LLM 输出）。

## 记忆与持久化分层设计

**MVP 范围收敛（2026-09-11 拍板）：MVP 记忆做 ① 对话记忆 + ③ 偏好记忆（上提），② 经验记忆后续再补。**

| 类型 | 内容 | 范围 | MVP 状态 |
|---|---|---|---|
| ① 对话记忆 | 对话框内多轮上下文 + 历史翻看 | 会话级 | ✅ MVP 做 |
| ② 经验记忆 | 「情境→教训」对（TradingAgents BM25） | 待定 | ⏸️ 后续再补（L3） |
| ③ 偏好记忆 | 风险偏好等（轻量） | 会话级 | ✅ MVP 做（**上提**） |
| ④ 业务数据 | 报告 / trace / 自选股 | 用户/应用级 | 非「记忆」，报告/trace 照做（可引用关联） |

**MVP 落地**
- 建 `conversation` / `message` 两张表：对话历史持久化 + 前端聊天框翻看历史（分页加载）。
- 阶段 3 的记忆工作缩到最小：**对话历史接进 LangGraph 消息流 + 落库 + 翻看**，长会话自动摘要压缩；不碰 jieba/BM25/向量那套。
- `memory`（经验）表从 MVP 移除，留到 L3 记忆增强。
- 已定：多用户/多会话框架照旧（`conversation` 带 `user_id`，支持多会话），记忆层 MVP 不做会话间联动。
- **偏好记忆上提（2026-09-11）**：③ 偏好记忆 MVP 做（轻量、会话级）——风险偏好等以 JSON 挂在会话/用户表，金融助手加载进 system prompt；不等 L3。
- **报告可引用关联（2026-09-11）**：`analysis_report` 落库带 `task_id` / `stock_code` / `conversation_id` / `rating` / `analysis_date`，金融助手能"引用"历史报告（"你上次分析过 X，结论是 Y"），同一会话框能知晓上下文。
- **会话上下文四类（金融助手可见）**：① 对话历史 ② 历史报告（本会话 + 用户曾跑过）③ 会话内产物（本次分析刚出的报告/评级/候选股）④ 轻量偏好。四类共同构成"知晓上下文"的输入。

**L3 再补（已定延后，不做 MVP）**
- ② 经验记忆：jieba+BM25（或向量）+ 事后验证闭环（用 `market_daily` 事后 N 日走势验证历史评级对错）；共享范围届时再定。
- ③ 偏好记忆已上提到 MVP（见上），L3 只补"跨会话/跨用户共享偏好"（如全局风险画像），落地届时再定。

## 全局知识库（B：自产报告检索）

> MVP 新增能力（2026-09-11 拍板）：把本服务跑出的历史分析报告沉淀成可检索的「全局知识库」，给 agent 加检索能力。这是「全局记忆」的落地，与经验记忆无关（不依赖反馈闭环）。

**落地设计**
- 落库：报告落 `analysis_report` 表时带结构化元数据 `stock_code` / `stock_name` / `industry`（申万行业）/ `board`（板块）/ `rating`（评级）/ `analysis_date`；题材标签 ❓ 后补（MVP 先用行业分类）。
- 检索：`retrieve_history` 工具 = 结构化过滤（SQL：行业/代码/日期）+ 关键词/语义匹配（BM25 + jieba，量级几千篇够用，量大了再 embedding）。
- 两个使用场景都支持：① agent 分析时主动调（加进基本面分析师工具列表）② 用户在对话框问历史（对话里 agent 调它回答）。
- 返回：最相关 N 条报告的「元数据 + 结论摘要」，**非全文**（避免 prompt 爆炸）。

**阶段安排**：阶段 0 预留元数据字段 → 阶段 4 报告落库填充 → 之后加 `retrieve_history` 工具 + 检索层。

**默认决策（可改）**：检索范围由工具参数控制，prompt 引导 agent 优先「同行业 + 同题材」；题材标签后补。

## 6. 关键坑与决策点（已识别，务必记牢）

1. **复权因子**：`market_daily` 无复权字段，技术指标/回测/选股因子必须用复权价 → 自建 `adj_factor` 表（QMT `dividend_type` 或 akshare `adjust="qfq"`）。
2. **中文记忆检索**：BM25 算法本身可用中文，**失效的是参考项目的英文分词**——`memory.py` 用 `\b\w+\b` 按空格切词，中文无空格会把整句当成一个 token，词频统计退化。改法：`_tokenize` 换 jieba 分词后 BM25 照常工作（低成本）；❓ 若要解决同义/近义词面不匹配（如「降息」vs「利率下调」），再换 embedding 向量库。
3. **SSE 采集时机**：`create_msg_delete()` 的 `RemoveMessage` 会在每个分析师后清空消息 → trace 必须在清空前抓取，否则中间思考过程丢失。
4. **symbol 格式不统一**：财务指标 `600025.SH`（后缀）、三大报表 `SH600025`（前缀）→ 数据层统一格式。
5. **akshare 接口名随版本变**：生产必须 `dir()` 自检 + 版本锁定 + 重试兜底。
6. **中文 Windows 控制台 GBK**：入口脚本 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，写文件 `encoding="utf-8"`。
7. **全市场初筛不碰实时快照**：东财反爬挂、新浪慢 → 用本地 `market_daily` 一次 SQL 算指标（快、稳、不限频）。
8. **volume 单位**：`market_daily` 的 volume 是「手」（×100 得股数）；ST 靠 `stocks.name` 的 `*ST` 前缀判断。
